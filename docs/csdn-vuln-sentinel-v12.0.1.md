# Vuln Sentinel v12.0.1：一款强调证据、复测与修复闭环的开源漏洞扫描工作台

> 本文介绍开源项目 Vuln Sentinel 的定位、核心能力、技术设计、适用场景与当前能力边界。请只对拥有明确授权的目标进行安全测试。

## 一、为什么做 Vuln Sentinel

很多漏洞扫描工具可以输出大量结果，但真正进入整改阶段时，经常会遇到几个问题：

- 只告诉你“可能有漏洞”，却没有足够证据；
- 误报和真实漏洞混在一起，开发人员难以判断优先级；
- 给出问题后没有明确的修复建议和复测流程；
- 扫描、报告、整改工单和复测结果相互割裂；
- 为了追求“漏洞数量”，忽略了结果是否能够复现。

Vuln Sentinel 的目标不是承诺“扫描所有漏洞”或“零误报”，而是做一套更适合实际交付的安全工作台：

> 从授权目标扫描开始，将发现结果、证据等级、修复建议、整改工单和复测验证串成一个完整流程。

项目目前适合安全演示、内部测试、中小团队安全体检和小范围交付。

## 三、核心能力

### 1. 基础 Web 安全体检

Vuln Sentinel 可以对授权站点执行常见安全配置与暴露面检查，包括：

- HSTS、CSP、X-Frame-Options、X-Content-Type-Options 等安全响应头；
- Cookie 的 Secure、HttpOnly、SameSite 属性；
- CORS 配置缺陷及预检请求验证；
- SSL/TLS 证书与弱协议检查；
- 敏感路径、备份文件、`.env`、`.git` 等暴露面；
- 页面注释、调试信息、错误栈和潜在信息泄露；
- 第三方组件与公开版本信息；
- HTTPS 页面加载 HTTP 资源等前端供应链风险；
- 跨域脚本、样式资源缺少 SRI 完整性属性。

其中安全响应头、Cookie、CORS 和 TLS 等检测主要基于真实响应头或网络握手证据，适合作为基础安全检查的稳定能力。

### 2. 攻击面发现

工具不仅检查首页，还会从公开信息中收敛攻击面：

- 分析页面和前端脚本中出现的 API 路径；
- 识别 `/api/`、版本化接口和 GraphQL 等入口；
- 检查 `robots.txt`、`security.txt`、`manifest.json`、`openapi.json`；
- 发现公开后台入口、登录入口和敏感接口；
- 对常见开放重定向入口和参数进行有限验证；
- 在深度模式下进行同源页面与参数发现。

这类能力适合用于接口资产梳理和攻击面收敛，但前端代码经过混淆、动态拼接或接口只在登录后出现时，仍可能存在漏报。

### 3. 注入类漏洞检测

当前已覆盖以下常见注入风险：

- SQL 注入：数据库错误特征、响应差异和有限时间特征；
- 反射型 XSS：检查 payload 是否原样进入响应以及所处上下文；
- SSTI：使用唯一渲染标记判断模板表达式是否被执行；
- 命令注入：检查响应中的命令执行结果特征；
- 路径遍历与系统文件特征；
- XXE 与 XML 解析风险；
- 不安全反序列化特征；
- SSRF 与云元数据响应特征。

项目已经为 SQLi、反射型 XSS、SSTI 和命令注入加入离线正负样本基准，验证检测器能够命中已知特征，同时不对安全响应产生误报。

需要注意：离线基准验证的是“检测规则契约”，不等于在所有真实网站、WAF 或复杂业务环境下都能达到相同准确率。DOM XSS、存储型 XSS、复杂盲注和需要业务状态的漏洞仍需要人工验证。

### 4. 身份认证与访问控制检查

Vuln Sentinel 提供部分认证和权限风险检查能力：

- 登录表单 CSRF、防点击劫持和基础防爆破检查；
- 后台与敏感接口匿名访问识别；
- IDOR 相邻对象与响应差异辅助分析；
- 双账号授权矩阵与结构化差异证据；
- JWT、会话、安全 Cookie 和认证配置检查；
- 管理员敏感操作二次确认；
- 登录、注册和验证码限流。

权限问题高度依赖业务语义。扫描器可以提供线索和对比证据，但真实 IDOR、水平越权、垂直越权和 MFA 绕过仍建议使用至少两个真实账号进行人工矩阵测试。

### 5. 结果可信度分层

Vuln Sentinel 不把所有命中项都包装成“已确认漏洞”，而是将结果分为：

- **已验证**：具有明确请求、响应或协议证据；
- **建议复核**：规则命中，但仍可能受页面结构、WAF 或业务语义影响；
- **待人工复核**：自动化无法可靠得出结论，需要人工验证。

报告还会展示：

- 实际抓取页面、接口和脚本数量；
- 实际测试的参数与检测类型；
- 超时、阻断和未覆盖项；
- 证据、风险说明和修复优先级；
- 管理层摘要和按风险面分组的结果。

这种设计的重点是让使用者知道“工具实际做了什么”和“哪些地方没有做”，避免把没有覆盖的范围误认为安全。

### 6. 修复、复测和工单闭环

扫描只是第一步，Vuln Sentinel 还提供：

- 针对不同技术栈的修复建议；
- 修复配置包和补丁生成；
- 修复前后结果对比；
- 重新扫描验证修复效果；
- 整改工单、负责人、复核人和状态流转；
- 批量导出整改摘要；
- 趋势统计、风险类型聚合和审计日志。

SSH 自动修复默认只生成补丁，不会直接修改远程服务器。只有用户明确启用并提交 `apply=true` 时才会执行写入操作。

### 7. 扫描任务与生产部署

在工程能力方面，项目支持：

- 标准扫描与深度扫描；
- 插件级超时隔离，单个慢检测器不会拖垮整次任务；
- 扫描暂停、恢复、取消和失败重试；
- Redis 队列中的任务恢复；
- PostgreSQL 生产数据库；
- Prometheus 指标和 Sentry 集成；
- Docker、GitHub Actions 和 Windows 安装包构建；
- 中英文 Windows NSIS 安装流程。

生产环境会检查关键安全配置，包括强 JWT 密钥、凭据加密密钥、显式 CORS 来源、HTTPS 公共地址、Redis、关闭支付 mock 模式等。开发环境默认只监听 `127.0.0.1`，demo 账号也不会自动创建，除非显式开启。

## 四、安全加固情况

项目近期完成了多项自身安全加固：

- URL 校验拒绝私网、回环、链路本地以及公网和私网混合解析结果；
- HTTP 请求包含 DNS pinning 与重绑定检查；
- `TLS_VERIFY=false` 时在结果中明确标记为跳过验证；
- 生产配置禁止通配符 CORS 和弱 JWT 密钥；
- 报告中的用户可控内容经过 HTML 转义；
- 公开演示扫描限制在白名单目标并写入审计日志；
- 支付回调使用事务化幂等入账，防止并发重复通知重复增加积分；
- 支付回调必须与订单原始渠道一致；
- 生产环境若支付参数配置不完整会拒绝启动；
- 生产环境强制使用 Redis，避免多实例限流和任务状态不一致。

当前完整 Python 自动化测试曾取得 **1356 passed、4 skipped**。跳过项是依赖本地 Nginx/OpenSSL 演示环境的测试，不是测试失败。Windows CI 已完成安装包构建、安装生命周期、PE 文件和 SHA-256 校验。

## 五、快速开始

### Windows 用户

1. 打开 GitHub Releases；
2. 下载最新的 `Vuln-Sentinel-*-win64-setup.exe`；
3. 运行安装程序，可选择简体中文或 English；
4. 打开应用，输入已经获得授权的目标地址；
5. 查看检测结果、证据、修复建议和复测入口。

卸载请通过 Windows“设置 → 应用 → 已安装的应用”，或开始菜单中的卸载入口完成。

### 源码运行

```bash
git clone https://github.com/tomjoy248-crypto/vuln-sentinel.git
cd vuln-sentinel
python -m venv .venv
```

激活虚拟环境后安装依赖：

```bash
pip install -r requirements.txt
```

开发环境启动：

```bash
python main.py
```

默认开发监听地址为 `127.0.0.1`，避免无意暴露到局域网或公网。具体命令和环境变量请以仓库 README 与部署文档为准。

## 六、适用场景

Vuln Sentinel 比较适合：

- 独立开发者和个人站长进行上线前安全体检；
- 中小团队进行基础安全检查与整改追踪；
- 运维、DevOps 团队检查 TLS、响应头、Cookie 和公开入口；
- 乙方安全团队生成初步证据与整改报告；
- 已修复漏洞的复测验证；
- 在明确授权范围内进行持续巡检。

它不适合被当作无人值守的“全漏洞证明工具”，也不能替代专业渗透测试、代码审计和业务安全评审。

## 七、当前能力边界

以下场景仍需要重点人工复核：

- WAF、CDN、验证码和复杂反爬环境；
- 软 404、大量跳转和不稳定页面；
- 强登录态、多步骤业务流程与 MFA；
- 复杂 IDOR、越权、竞态和支付业务逻辑；
- DOM XSS、存储型 XSS、复杂 SQL 盲注；
- 大型单页应用中的动态接口和动态表单；
- 真实支付宝、微信支付 SDK 验签与沙箱回调。

真实支付目前仍需要商户沙箱证书、公钥、私钥、API v3 密钥和公网 HTTPS 回调环境完成最终验收。没有这些材料时，系统会安全拒绝未实现或配置不完整的真实回调，不会将其错误标记为支付成功。
